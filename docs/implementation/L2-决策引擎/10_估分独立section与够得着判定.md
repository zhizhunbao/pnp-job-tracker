# L2-10 · 估分独立 section 与「够得着」判定

> 立项:2026-08-16 Frank「还是需要估分 和之前捞人的历史记录的,如果用户分数达标 就等着被捞,
> 不需要换省份找工作了」+「估分的答题和结论 放到单独一个 section,不要和基础题放一块」。
> 主线判据([主线与支线](../../主线与支线-20260801.md)):这是**结论层**的一格 —— 「该不该为这个省换工作」
> 是用户真正要的决定,而在此之前估分虽然算了、上了页,却对排序与结论**零影响**(见 §2)。

## 1. 目标与非目标

- 目标:估分与抽选线合成**一个能落地的结论** —— 够得着就说「留在池子里等」,够不着就说差多少。
- 目标:估分的答题与结论从「申请人条件」里拆出来,独立成 section,两段计数各算各的。
- 非目标:预测多久被捞、给概率(禁概率红线);改动 BC/ON 那类算不出分的省(它们缺岗位侧输入,另立)。

## 2. 病灶(为什么改)

盘生产数据时发现的:估分这功能**看起来在跑,实际上没接上**。

1. `belowLine` 两头都拿 `value` 判,又要求 `!partial`。而 `partial` 的含义是「本省表里有加分项 →
   value 是**下界**」—— AB 的官方表带 12 条加分项 ⇒ 恒 `partial` ⇒ **沉底永不触发**。
2. 「够得着」这一侧压根没写过。
3. 于是六省分值表(222 行)入库、上页、参与不了任何排序;而通用估分器真接得上的只有 AB 一个省
   (ON/BC/SK/NL 的必答档位从档案喂不出来,见 [pathVerdict.ts](../../../cms/src/lib/pathVerdict.ts) 文件头)。

## 3. 方案

### 3.1 判定:两头各取各的那一侧([lib/scoreLine.ts](../../../cms/src/lib/scoreLine.ts),新)

| 态 | 判据 | 为什么是硬结论 |
|---|---|---|
| `above` 够得着 | **下界** ≥ 线 | 加分项只会更高,partial 与否都成立 |
| `below` 够不着 | **上界** < 线 | 全按满分也摸不到线 |
| `unknown` 留白 | 下界 < 线 ≤ 上界 | 取决于加分项,**不许**归到任何一头 |

缺一边(没分/没线)一律 `unknown`,不拿空当 0;`ceiling` 算不出时退回 `value` —— 宁可不沉,不误沉。

### 3.2 排序:够得着**只在档内**提前([lib/planRank.ts](../../../cms/src/lib/planRank.ts))

次序插在 band 之后、thin 之前(新 ⑤)。不跨 verdict、不跨本省优先 ——
分够不够是「多久到手」,不是「能不能走」,拿它翻越前面的主键会把走不了的路捧到前排。

### 3.3 展示:独立卡([ScoreLineCard.tsx](../../../cms/src/app/(frontend)/plan/pr/ScoreLineCard.tsx),新)

三层,顺序即优先级:① 该省近 6 轮抽选线(**未答题也给看**,官方事实免费)→ ② 你的估分 →
③ 一行结论(三态各说各的)。省份页签:有分值表的在前,只有线没有分的省也进(线本身值钱)。

计数拆开:摘要卡只报基础段 `stepDone/stepTotal`,估分段的 `scoreDone/scoreTotal` 归这张卡 ——
合并成 17 项时看不出人卡在哪一段,而那正是要改哪一边的唯一依据。

**容器恒定**:分值卡实例常驻在这张卡里,所以卡不许「一会儿在、一会儿不在」(那是 React 重挂 =
答案清零)。省没选/没表时卡自己退化成一句提示,不搬树。带岗态照旧走判定卡的 `scoreSlot`,不渲第二份。

## 4. 红线

- 结论**只到「够不够线」为止**:不许延伸成「多久能被捞」「概率多大」。
- 分与线都必须是官方事实(分=官方分值表,线=官方抽选史);没线的省一律留白,不编。
- 下界不许拿去判「够不着」,上界不许拿去判「够得着」—— 两头用反就是这次修的病。
- 未答题的空态给**事实**(近 6 轮线),不给「请先答题」。

## 6. 落地记录

### 加分项回流(2026-08-16 同日补,Frank 拍第 1 条)

上线当天生产实测暴露:服务端估分只吃**档案**,而加分项(AB 那 12 条:亲属在本省、offer 地区/行业、
受监管职业…)是用户在估分段**勾**的,勾选留在分值卡的 localStorage 里、从不上行 ⇒ 服务端一律按
「没勾=0」算 ⇒ 强档案(CLB10/硕士/10 年经验)在 AB 也只有下界 46 对线 53,恒落 `unknown`。
后果:「够得着」只有联邦 EE 说得出口(CRS 没有要勾的加分项)。

修法取第 1 条(把勾选做成正式答案字段随请求上行,服务端按它算),四处接线:
- `PrDecisionView`:勾选签名进重算边界(`tickSig`),值随 `/api/profile-pathways` 上行;
  挂载与每次答题回报时从 `readScoreAnswers()` 同步
- `route.ts`:**信任边界校验** —— 键须匹配 `省:因素:批`、只收 `true`、总量封顶 64
  (它直接进分值计算,放任自由文本进来等于让请求方自己写分)
- `pathVerdict`:`VerdictProfile.scoreTicks`,喂给 `scoreProvince` 的 now 那一侧;只取本省的键
- 没勾的仍按 0 ⇒ value **仍是下界** ⇒ 「够得着」照旧是不会翻案的硬结论,三态口径一个字不用改

单测 4 条(真数据):AB 表确带加分项、勾了下界必涨且上界不动、别省的勾一分不算、勾满过线转 `above`。

**生产实测(部署后同一份档案对打)**:勾之前 AB 下界 46 对线 53 → `unknown`;勾满 7 条加分项后
下界 **98** 对线 53 → **`above=true`**。同一请求里混进的脏键(`__proto__`、`evil key`、别省的
`BC:wage:0`)全部被挡在校验外,分毫未进 AB 的分。至此「分够了就等着被捞」这句话**第一次对省提名
也说得出口**,不再只有联邦 EE。
