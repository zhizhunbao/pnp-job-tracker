# 七个决定各要哪些问题(题库矩阵)

> 2026-07-31 Frank:「还有那个建档的功能都是重复的」「这个怎么统一设计一下」「你是不是应该先设计一下每个决定都需要哪些问题」。
> 本文先定**问什么**,不定 UI。承接 [L2-02 题库](../implementation/L2-决策引擎/02_题库.md) 的铁律与 [架构 v2](../产品架构v2.0-决策智能平台.md) 的七目标。

## 0. 为什么现在重复

同一批字段,站内有**三套问法各自维护**:

| 在哪问 | 问什么 | 存哪 |
|---|---|---|
| EntryQuiz 三问弹框 | 处境、职业、目标省 | localStorage `jobs_quiz_v1` |
| /plan/pr 基本 4 题 | 处境、英语、加拿大经验、目标省 | localStorage `plan_pr_v1` |
| 建档向导 / /account 档案 | 上面全部 + CRS 等 | DB users.profile |

**处境问两遍、目标省问两遍**,而且三处的档位切法还不完全一样。这不是 UI 问题,是没有「字段单一来源」。

## 1. 铁律(不变)

1. **每题必改结论**:一道题若不改变任何一条能算出来的结论,就不问(学历、法语当前无规则 → 不问)。
2. **问过的不再问**:字段属于用户,不属于某个页面。进任何决定前只补它缺的字段。
3. **算不出就别问**:没有数据支撑的结论,对应的题一律不上(见下表「数据缺口」列)。

## 2. 字段库(全站单一来源)

| 字段 | 档位 | 谁在用 |
|---|---|---|
| `nocs[]` 职业 | 搜索选 | 找工作、拿PR、选省份、选城市、职业规划 |
| `currentStatus` 处境 | 境外 / 读书 / 工作 / 找工作 | 全部(决定哪些通道与信号相关) |
| `targetProvinces[]` 目标省 | BC / ON / 草原 / 不限 | 全部 |
| `clb` 英语 | 初 / 中 / 流利 / 没考 | 拿PR、选省份 |
| `canadianExpMonths` 加拿大经验 | 无 / <1年 / 1-2年 / 2年+ | 拿PR、选省份 |
| `crs` EE 分 | 没算过 / <400 / 400-450 / 450+ | 拿PR |
| `pgwpMonthsLeft` 签证剩余 | <6月 / 6-12月 / 1-2年 / 2年+ | 拿PR、选学校 |
| `hasJobOffer` 有无 offer | 有 / 没有 | 选省份(雇主通道开不开) |

前三个是**共用底座**——正是老三问在问的那三题。它不该属于某个弹框,而应是全站字段库的必答子集。

## 3. 七个决定 × 需要的问题

| 决定 | 共用底座 | 专属题 | 能出的结论(现有数据) | 数据缺口 |
|---|---|---|---|---|
| **找工作** | 职业、处境、目标省 | 无 | 在招岗 + PNP/LMIA/EE 信号 + 薪资对比 | — |
| **拿 PR** | 同上 | 英语、加拿大经验(基本);CRS、签证剩余(探索) | 清单命中四态、抽选线区间/分差、时间窗、备选省 | 各省语言与工资门槛未建模 |
| **选省份** | 同上 | 有无 offer | 十省对照:清单命中、在招量、抽选线区间、难度分 | 省级生活成本 |
| **选城市** | 职业、目标省 | **不加题** | 城市对照:在招量、ESDC 中位薪资、具名清单岗数 | **房租/生活成本没有** → 城市决策目前只是选省份的下钻 |
| **选学校** | 处境、目标省 | 签证剩余 | 295 所 DLI:省份、公私立、有无 grad program(→ 毕业生通道) | **学费、专业目录都没抓** → 预算题现在问了也算不出,不上 |
| **职业规划** | 职业、目标省 | 无 | 职业对照:在招量、TEER、中位薪资、PNP 命中、EE 类别 | 职业转换路径(A→B 的可行性)无数据 |
| **选专业** | — | — | **无** | 专业→职业映射没有 → 保持灰态,不上假入口 |

### 从矩阵读出的三条结论

1. **专属题只有拿 PR 多**(4 道)。选省份多 1 道,其余决定的题**已经被共用底座覆盖**——所以不需要七套题库,只需要一套字段库 + 每个决定声明它要哪几个字段。
2. **老三问不该删,该升格**:它问的正是共用底座。把它从「某个入口的弹框」改成「全站字段库的必答子集」,重复问题自然消失。
3. **两个决定现在不配有题**:选城市(没有生活成本数据,只能做省份下钻)、选专业(没有专业映射)。硬加题就是问了不改结论,违反铁律。

## 4. 落地形态(不改 UI,先定结构)

```
lib/questions.ts   字段库 = 每个字段一段 JSON(题干、档位、映射)——单一来源
                   每个决定 = 一个字段名数组(DECISION_FIELDS.pr = ['noc','status','clb',...])
渲染器             SurveyJS 一个;弹框态与页内态是同一渲染器的两个容器
入口               landing 卡 / 职位板建档 / 决定页 —— 都进同一答题器,
                   差别只有「至少要答哪些字段」和「答完去哪」
存储               localStorage 一份(匿名)→ 登录后落 users.profile 一份;不再一页一个 key
```

进入任何决定时:读已知字段 → 只问缺的 → 答完直接出该决定的结论。用户第二次进另一个决定时,只会被问到新字段。
