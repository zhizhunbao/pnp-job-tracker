## D. 本轮立的两条铁律(已进 memory 与《主线与支线》§1.5)

1. **补全数据 + 保鲜 = 永久主线**,不参加支线分诊。缺数据当场抓;**对客户永远先给答案,不许说「本站未收录」**(那是我们的库存报告,不是他要的答案)
2. **抓完必须当场进 docker 定时役**,不许「抓一次完事」。交付前自查一句:这次抓的东西,明天还会自己更新吗?
   配套:抓数据一律先用仓库现成的 `etl/crawl/` 工具链(bfs_crawler 探 URL / download_md 转 md / browser_fetch 兜底),不临时手写 httpx;官网被反爬挡住先试**文件服务器**(PEI 那 8 个 NOC 就藏在官方指南 PDF 里)

3. **挂进 META ≠ 会跑**(当天实撞):`auto_update.py` 长驻,启动时 import 一次 META,steps 从此冻结。
   改了 steps **必须 `docker restart pnp-<role>-1`**,否则新步骤永远不执行,而容器 healthy、ping 正常、
   日志里也看不出少跑了什么 —— 这是本轮最隐蔽的坑(见 B3-4)。**交付自查:`docker logs pnp-<role>-1 | grep "→ python"`
   确认那一步真的出现过**,不能只看代码挂上了。

## E. 本轮教训(给下一个 session 省时间)

- **数行数猜覆盖=会撒谎**:同一次会话里助手两次把部分数据当全量(SK 三条行业专项当全省清单、AB 排除清单当清单式省)。口径必须写在数据里,人和引擎都只能从行数猜时,就都会猜错
- **排序目标不许助手拍**:写死过两版都错。「每个人诉求不一样」——目标函数是用户的输入,不是我们的常量
- **注释会撒谎,测试不会**:`decisions.ts` 的注释说四道题「都真的进分值表」,实测消费 0 次。今天把「字段必须被 builder 真实消费」这件事往测试里挪了一步(`rpt.p.*` 进白名单),但**还没有自动校验 unlocks 与引擎实际产出的一致性** —— 值得单独立项
- **数据变好会让断言过期**:补了 BC 排除清单后,我自己 20 分钟前写的测试立刻失效(BC 从 partial 变 exclusion)。这是对的,断言跟着数据变强
