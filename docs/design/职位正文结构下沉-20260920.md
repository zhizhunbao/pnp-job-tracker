## 一、用户故事

小王在手机上点开一个护士岗,想三秒看完「给多少钱、干什么、要什么条件」。他看到的是 30 行等距的英文句子,四个节头里只有一个是粗的,其余三个混在句子中间;他往下滑了两屏,放弃,退回板上。

小李点开一个 Jobillico 的法语岗,看到的是**一整坨没有任何分行的字**——「Les défis qui vous attendent Effectue divers travaux…」,节头「你将面对的挑战」直接粘在第一句话上,连个句号都没有。

两个人看到的不是排版问题,是**我们在抓取时把原帖的结构扔了**。原帖两边都是规规矩矩的 HTML。

### 病根:同一个行为,六个域,五份复制,五份都错

```python
# etl/jobillico/functions.py:281 · etl/jobboom/functions.py:275
# etl/careerbeacon/functions.py:288 · etl/hireac/functions.py:403   ← 四份逐字相同
return WS_RE.sub(SPACE, unescape(TAG_RE.sub(SPACE, html))).strip()   # 标签→空格,换行也→空格

# etl/ats/functions.py:111  ← 第五份,只差保留了源头自带的换行
return BLANK_LINES_RE.sub(PARA_SEP, TAG_RE.sub(SPACE_SEP, html)).strip()

# etl/jobbank/functions.py:716 serialize_node  ← 唯一做对块级的,但只认 h1-h6 / li,不认 strong
```

`WS_RE.sub(SPACE, …)` 把换行一并吃掉 —— 这就是 Jobillico 100% 一行的原因。ATS 那份没吃换行,所以现在还有 32 行,**但那 32 行是 Phenom 的 HTML 自己带的换行,厂商哪天把 HTML 压一行,整帖立刻退化成一坨**(3,251 字符)。我们没有在依赖自己的解析,是在依赖对方的排版习惯。

CLAUDE.md:「行为(函数)重复不许」。这里是五份。

### 节头在源头是写得死的

`data/crawl/ats-sienna-senior-living/html_cache/`(498 页原文在盘上)里,Sienna RPN 那帖:

```html
<p><strong>What We Offer:</strong></p>
<p>Reporting to the Director of Care, the <strong>Registered Practical Nurse</strong> is a critical role...</p>
```

一个是节头,一个是行内强调,**形态上完全分得开**。现在两个都被碾成空格 —— 库里 `jobs.id=60891959` 的正文,节头行首尾各留 2 个空格、普通段落 1 个,那两个空格就是 `<strong>` 的尸体。

## 三、判据(节头怎么认)

> **一个块级元素的可见文本 == 它内部 `strong`/`b`/`h1-h6` 的文本 → 节头;否则是行内强调,不标。**

一句话,零白名单、零猜。对上面两行 HTML 一个判真一个判假。

这条判据同时解释了为什么**前端补不了**:前端拿到的是纯文本,`<strong>` 早没了,它只能靠「白名单 + 带冒号」猜 —— Sienna 那帖四个同级节头,只有 `What We Offer:` 因为碰巧带冒号被认出来,`What you'll be doing:` 因为撇号是弯引号 `’` 落选,`Who you are` / `What you need to know` 因为没冒号落选。**一粗三不粗,比四个都不粗更难看。**

## 四、方案

### 1. 新立基建叶 `etl/richtext/`

**边界三问**(CLAUDE.md 要求,不判边界不许新建域):

| 问 | 答 |
|---|---|
| 回答什么问题 | 一段 HTML → 带结构的纯文本(段落落换行、列表 `• `、节头 `## `)。 |
| 和已有域边界切在哪 | `fetch` = 拿已知 URL(网络);`crawl` = 找未知 URL + 存原文(发现与缓存);`richtext` = 把原文变成结构化文本(解析)。切法是**网络 / 发现 / 解析**三刀,不是「哪个源」——源会生灭,这三件事不会。 |
| 寿命多长,谁先死 | 源域先死(HireAC 可能停、新板会接)。HTML 不死。依赖方向 `各源域 → richtext`,指向活得更久的那个,合规。 |

闸:`etl/gate/constants.py:45` 的 `INFRA = {"paths","fetch","log","noc","crawl","names"}` 加一个名字 —— **加名过 Frank**(CLAUDE.md 立的规矩,本稿就是来要这个点头的)。

**域名(2026-09-20 Frank 问「叫 html 名字合适吗」后改判)**:定 `richtext`。

- 🔴 **`html` 直接排除,硬理由**:`etl/` 是 `sys.path.insert` 进去的,域以**顶层包名**被引 —— `etl/html/` 会遮蔽 Python 标准库的 `html`。仓里 10 个域 import 它(ats:21 / careerbeacon:19 / hireac:20 / jobboom:15 / jobillico:15 / aip:23 / company:20 / fcip:33 / gcjobs:19 / mart:33),其中**前五个正是本批要接线的域**,全是 `from html import unescape`,接线当天整域起不来。
- 按命名规矩它本来也不合格:六片叶子没有一个按输入介质命名(paths 装路径、fetch 做抓、log 装日志、noc 本名、names 装名字、crawl 做爬);CLAUDE.md 禁共享叶子叫 `json.ts`,禁的就是「拿格式/介质当名字」。
- **`richtext` 是本名**:jobbank 那个做对了块级的函数 2026-07-16 起就叫 `rich_text`,docstring 写「块感知提取:HTML 结构 → 带换行的纯文本」。域名照本名,正门 `from richtext.functions import rich_text`;venv 内无同名包。
- 否掉的其余候选:`jdtext`(绑死 JD —— `etl/sites/functions.py:593,844` 的官网正文提取是同款第六份,这把工具不是 JD 专用)、`markup`(同 html,说介质)、`article`(业界指「正文提取」,但提取是各域的事,我们只做序列化,名不副实)、`text` / `body`(太泛)、`serialize`(说动作不说对象)。

## 八、落地记(2026-09-20 实做)

### 1b 判据 —— 实测

新增 `is_head_block`:块的可见文本 == 块内 `strong`/`b` 文本且 ≤ `HEAD_MAX_LEN`(80)= 节头;`h1-h6` 同样落标记。

### 换装批的「值不变」怎么证的

换装批的验收口径是**值不变、形归一**。两道探针跑在 crawl 缓存的真页面上:

| 探针 | 范围 | 结果 |
|---|---|---|
| 内容丢失 | jobillico 1,498 + jobboom 1,487 + careerbeacon 50 + phenom 498 | **新解析吐空 0 页**(一帖正文都没丢) |
| 字符集逐字比对(只留字母数字) | 同上 **3,533 页** | **相同 3,533 · 不同 0** |

第二道是决定性的:去掉空白与标点后新旧一字不差 = **内容一个字没变**,变的只有结构。

字符级相同、但词级看着「丢词」的 970 页,差异全是旧法把标签替成空格造成的标点粘连
(旧 `Benefits :` / 新 `Benefits:`)。其中一类新法更对:旧文本里 `Associate Director of Car</strong>e`
被切成 `Car` + `e` 两个词,新法还原成 `Care`。

行数(抽样):jobillico 均 **1.0 → 33.8**、jobboom **1.0 → 33.5**、careerbeacon **1.0 → 34.1**。
(phenom 那一档的「改前」在探针里按 jobillico 式旧法算,不是 ats 的真实旧行为 —— ats 那份保留了源头换行,实际约 32 行;节头数是真的:498 页 2,135 条。)

### 追加一:markdown 星号也是节头(2026-09-20 深夜,Frank 三次实拍)

雇主在招聘板的正文框里用 **markdown 星号**标加粗。「整行被星号包住」= 节头,「行内被星号包住」= 正文 ——
**判据与 HTML 的 `<strong>` 一字不差,只是介质换了**。而 jobbank 的 `lined_text` 把星号一律剥光,
节头信息就地蒸发;前端只能靠「碰巧带冒号」捞回一半(`Experience:` 捞到、`Qualifications` 丢了),
`Responsibilities` 之所以还粗纯粹因为它碰巧在白名单里。

处置:判据写成 `richtext.md_head_of`(一份实现),**两个调用方**共用 ——
jobbank 的 `lined_text`(在剥星号之前)与 mart 的 `mend_jd_line`(跨源兜底)。护栏两道:
去记号后 ≤ `HEAD_MAX_LEN`、不以句末标点结尾(整句被加粗的营销话术不是节头)。

| 验 | 结果 |

### 回溯:存量不会自愈,所以三个板域各加了一个手动件

Frank「不能开个脚本把存量修复一下吗」。查下来**必须**有这个脚本 —— 三个板域的 parse 都是增量的
(`if pid in facts: skipped`),换了解析器之后**库里那 2.4 万条永远不会被重新解析**,光重启容器只管新岗。

于是 jobillico / jobboom / careerbeacon 各加 `--only reparse`:缓存里的帖全量重解析、覆盖既有事实。
`ParseIn(force)` 一格分两档,例行链仍走 `force=False`,行为一字不变。住进域里当手动件,不在根上开散件
(先例:ats 的 `--only jd_index`、jobbank 的 `REPARSE_IDS`)。

**无损性已核**:三域的 JobFact 每一格都从缓存的 ld+json 重新派生,没有「只有首抓才有」的字段;
译名另住 `titles_en.json`,按帖号增量,不受覆盖影响。

各源的回溯方式不同,别一刀切:

| 源 | 存量怎么修 | 容器要不要先 restart |
|---|---|---|
| jobillico / jobboom / careerbeacon | `--only reparse`(读缓存,零网络) | 不是前提 —— 例行 parse 跳过已有帖号,旧代码容器不会把修好的盖回去;restart 只为让**新岗**也走新解析 |
| ats | 不用加件:每轮都从缓存重新派生,restart 后一轮自愈 | **必须** —— 不 restart 的话容器会继续用旧代码产出旧正文,把修好的盖回去 |
| jobbank | **建议不回溯**(见下) | 只为新岗 |

**jobbank 建议不回溯**:4.7 万条,`REPARSE` 全量 09-19 实撞十几小时 + 占仓锁堵死汇装;而它现在零节头率就是 0%
(白名单本来就管得住),收益最小。留欠账让它随自然滚动更新。这一刀把上线成本砍掉一大半。
