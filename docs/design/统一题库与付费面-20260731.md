## 0. 现在为什么收不上钱

不是价格问题,是**付费面太小、锁区太抽象**:

| 症状 | 根因 |
|---|---|
| 七个决定只有卡②「拿 PR」有报告 | 付费墙全站只有一处,用户撞不到第二次 |
| 答完 4 题就撞墙 | 探索题只有 2 道,答题带来的「又算出一点」体验只有一轮 |
| 锁区像「还没算出来的东西」 | 免费区没有一处证明「你的答案真的被用上了」 |
| 30 天包卖一份报告 | 一份报告值不了 30 天,用户心里算得过来 |

题库是这四条的公共上游 —— 所以先设计题库是对的,但**题库要按「喂付费引擎」来设计,不是按问卷来设计**。

## 1. 三条主张

### 主张 1:每道题带三个标签,不是只带字段

```ts
FIELD.crs = {
  q: { …SurveyJS 题 JSON… },
  unlocks: ['rpt.c.eeAbove', 'rpt.c.eeBelow'],   // 答完能算出哪几条结论(key 就是引擎里的 key)
  tier: 'pro',                                    // 那几条结论落在免费区还是锁区
}
```

- **挂不上任何结论 → 不入库**(旧铁律,不动)。
- `tier: 'free'` = **留存题**,答完立刻多一条能看的结论 —— 建立「答题有回报」的条件反射。
- `tier: 'pro'` = **转化题**,答完锁区从「还没算」变成「已经算好了,就差解锁」。
- **排序规则:每批探索题第一道必须是 free 题。** 先兑现一次,再谈钱。全批都是 pro 题 = 用户答了一批什么都没多看到,这是最伤的一种体验。

### 主张 2:付费面横向扩,不给拿 PR 纵向加题

矩阵已经证明:**找工作、职业规划零新题,选省份只多 1 道题**(`hasJobOffer`),就能出报告 —— 因为共用底座(职业、处境、目标省)已经覆盖。

所以最短的收费路径不是给拿 PR 再加 8 道题,而是**用同一个 `Report` 契约把这三张卡的 builder 写完**:

| 决定 | 新题 | 免费区(库里查得到) | 锁区(拿你的答案算出来) |
|---|---|---|---|
| 拿 PR(已有) | — | 清单命中、抽选线区间 | 分差、时间窗、备选省、EE 分差 |
| 找工作 | 0 | 在招量、薪资 vs ESDC 中位、具名清单岗数 | 按你在意的维度排序的岗位短名单、有担保记录的雇主 |
| 选省份 | 1 | 十省在招量、各省清单命中四态 | 十省**对你**的排序与差距、抽选线差分 |
| 职业规划 | 0 | 相邻职业的在招量、TEER、中位薪资 | 与你现职的差距(证书/语言/年限)与先后顺序 |

付费面 1 张卡 → 4 张卡,题库几乎不动。这是「我要收费」的最快落点。

### 主张 3:一次答题,处处解锁 —— 这才是 30 天包的理由

字段库统一后,用户在拿 PR 答的那 4 题,进「选省份」时不再问,**直接出报告**。于是:

- **免费用户**:四张卡各看前 2 条结论 = 8 条真结论,信任在这里建立。
- **付费用户**:一次订阅解锁四张卡的全部锁区。卖点从「解锁这一份报告」变成「**解锁你的全部决定,30 天内随便改答案重算**」。

**改答案重算**是复购锚:身份会变(考了雅思、拿到 offer、换省),报告跟着变才有 30 天的意义。

## 2. 免费 / 付费线(报告内口径,不改职位板既有 Pro 额度)

> **一句话口径:库里查得到的免费;拿你的答案算出来的付费。**

| | 内容 | 为什么 |
|---|---|---|
| 免费 | 画像、在招量、清单命中与出处、抽选线区间、中位薪资、**前 2 条结论**、全量缺口与下一步 | 这些不答题也查得到,收费站不住脚;缺口与下一步免费是诚信底线(告诉人差什么不该收钱) |
| 付费 | 分差、时间窗、备选省排序、EE 分差、省际/职业对照的**个人化排序** | 每一条都必须有用户字段才算得出;没有答案就没有这条,天然解释「为什么答题越多越该付费」 |

这个口径比旧的「事实免费、结论收费」更可执行 —— 旧口径答不了「中位薪资算事实还是结论」,新口径一句话就分完。
**边界声明**:本口径只管报告与题库,`/jobs` 的 Pro 额度、`/stats` 的免费图表照旧,不在本设计范围内改。

**红线(v2c 已立,继续守)**:锁区为空时不出 CTA —— 没算出东西就不卖东西。

## 3. 结构(代码形态)

```
lib/fields.ts       字段库 = 每字段一段 { q, unlocks, tier } —— 全站单一来源
lib/decisions.ts    每个决定 = 字段名数组:{ basic: [...], explore: [[批1], [批2]] }
lib/questions.ts    退化成「按 decision + 已知字段 → 拼出 SurveyJS JSON」的组装函数
渲染器              SurveyJS 一个(已在跑);弹框态与页内态 = 同一渲染器两个容器
入口                landing 七卡 / 职位板建档 / 决定页 —— 同一答题器,
                    差别只有「至少要答哪些字段」与「答完去哪」
存储                localStorage 一个 key(匿名)→ 登录落 users.profile;不再一页一个 key
```

进任何决定:**读已知字段 → 只问缺的 → 答完出该决定的报告**。加一张卡 = 加一行 `DECISION`,渲染层零改动。

## 4. 答题界面要加的两处钩子(效果图见 §7)

1. **进度条下一行「答这题能算出什么」**:`再答 2 题 → 算得出你差多少分`。
   写「算得出」不写「解锁」—— 这是诚实的差别:题的价值是让引擎算得出,付费才是看结果。
2. **每批答完回报告顶部一行变化提示**:`新增 3 条结论  置信度 中 → 高`。
   让「答题 → 报告变厚」这件事被看见,否则用户不知道自己刚才那批题换来了什么。

## 5. 不做什么(先写死,免得后面手痒)

- **不为了多一个锁区而加题**。题必须先能改结论,再谈它锁不锁 —— 反过来就是骗钱,也一定会被看穿。
- 不加学历题、法语题:引擎当前无规则,答了不改任何结论。
- 不上打字输入题(全四选一不变)。
- 选城市不加题(没有生活成本数据,只是选省份的下钻);选专业保持灰态(没有专业→职业映射)。
- 选学校不问预算(学费与专业目录都没抓)。

## 6. 矩阵三条待拍 —— 我的取舍

| 待拍 | 我定 | 理由 |
|---|---|---|
| 矩阵是否定稿(选城市/选专业不上题、选学校不问预算) | **照此定稿** | 数据缺口是硬的,加题=问了不改结论 |
| 职位板「建档案精确匹配」入口并入还是保留 | **保留入口,换成同一答题器** | 重复的是题不是入口;入口是转化位,砍掉少一个口。差别只有答完回职位板匹配视图 |
| 三个 localStorage key 收敛,老答案迁不迁 | **迁,一次性合并后删旧 key** | 老答案是用户唯一资产;丢了=让他重答 4 题,直接违反「问过的不再问」。优先级 profile > `plan_pr_v1` > `jobs_quiz_v1` |

1. **字段库落地**:`fields.ts` + `decisions.ts`,拿 PR 先切过去(行为不变=回归基线),旧 key 迁移。
