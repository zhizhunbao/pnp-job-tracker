## 1. 用户故事(验收:先 375px,再电脑;先英文)

1. **第 1 步 简历(B2)**:作为第一次投递的人,我进到这一岗的投递页,先看到本岗职位卡,下面只有一个「上传简历」钮。传一份 PDF 或 Word(5 MB 以内)后,显示文件名(点开能看)、上传日期和「替换」。第一次投递还要填英文姓名(§7 Q2),并答三道点选题:工作身份、最快什么时候能全职上岗、工作年限。

2. **第 2 步 求职信(B2)**:作为求职者,我看到一整封信,本岗的职位名、公司名和我的姓名已经填好,直接在多行框里改。框里有写不进 PDF 的字(中文、表情)时,框下一行列出是哪几个字,「Preview」变灰。

3. **第 3 步 预览(B2 只能看,B3 才能发)**:作为求职者,我看到职位卡(标题、译名、公司)和附件卡(简历文件名、`Cover_Letter_<公司>.pdf`),两个都能点开看。主钮「Send」,点了才发出。
   - 验收:点开求职信 PDF,文字和框里逐段一致,空行原样保留;长信自动分页。
4. **第 4 步 已投递(B3)**:作为求职者,点「Send」之后 H1 换成「Applied」,本岗职位卡右上挂绿色「Applied」标签,底部主钮变「My applications」,下面接同公司、同省同职业的相关职位卡。雇主收到的信来自「<英文名> via Offer2PR <apply@offer2pr.com>」,附简历和求职信 PDF。
   - 验收:用 @test.local 测试号点 Send,收件方被换成 `delivered@resend.dev`,Resend 后台日志能看到两个附件;同一岗连点两次只发出一封;回到职位页,投递钮显示「Applied」。
5. **以后再投(B3)**:作为投过一次的人,我在另一岗点「Apply」,直接落在预览一步,求职信已经按新岗换好,一点就发;想改就点「上一步」。
   - 验收:第二个岗打开就是 `?step=preview`,PDF 里是第二岗的职位名和公司名,我在第一岗改过的句子都还在。
6. **我的求职(B3)**:作为求职者,我在「我的」→「我的求职」里看到投过的岗,一张职位卡一个岗,右上一个状态(已投递 / 雇主已回复 / 退信),雇主回复的排最前,点卡回职位页。
   - 验收:375 英文,投过 1 封就是 1 张卡、状态「Applied」;没投过显示一行空态和「去职位板」。
7. **回信转发(B4)**:作为求职者,雇主回信时我的邮箱收到转发(标题带岗位名);我直接回复那封转发邮件,雇主看到的还是同一串往来;这一条变成「雇主已回复」。第一次投递前,预览一步告诉我「雇主回信经 Offer2PR 转给你,我们记录回复情况」(属于法律知情句,文案规则允许留)。
   - 验收:Frank 用私人邮箱给某条测试投递的 reply-<令牌> 地址写信,1 分钟内测试号邮箱收到转发、标题含岗位名;回复它,私人邮箱收到的还是同一串;在 Resend 后台把这次回调重放一次,不会再转发一遍。

## 2. 数据

### 为什么走原生 SQL(lib/db),不建 Payload collection

- Payload 没有二进制字段。Media 是 `upload:true`,文件落在本地磁盘,而且所有人可读(`cms/src/collections/Media.ts:3`、`:15`);Render 每次部署都会清盘。
- employer_email 不能出现在任何能通过 REST 读到的 collection 里。B1 抹邮箱那次就是同一类泄漏(付费闭环稿「10-04 B1 收口」)。
- 先例:`docs/sql/employer-explore-20260918.sql:6`(写明不是 collection)、users.pte_done 的读写(`cms/src/lib/db/sql.ts:2870`、`cms/src/lib/pte/functions.ts:61-79`)、funnel_events(`docs/sql/m2-funnel.sql:6`)。
- 这几张表不进 seed,所以 `payload_locked_documents_rels` 不用补列(要补的只有 collection 表和 seed 灌的表,见 `cms/src/lib/mart/functions.ts:1132`)。
- 🔴 drizzle 看不见原生表,`DB_PUSH=1` 会提议删掉它们,一律答 N。
- **简历原件存成 base64 文本,不用 bytea**。先例是 `docs/sql/pte-audio.sql` 的 b64 列,读出时用 `Buffer.from` 解回(`cms/src/lib/pte/functions.ts:122`)。理由:`SqlParam` 里没有 Buffer(`cms/src/lib/db/types.ts:48`),用文本就不用动这个叶子;Resend 的附件本来就要 base64,发信时不用再转码。代价是体积多 33%。这一条和 09-23 稿写的「bytea」不同,以本稿为准。
- **求职信模板和英文署名单独放一张 apply_prefs 表**,不并进 user_resumes。这样每张表只有一个域写:简历域写 user_resumes,投递域写 apply_prefs 和 applications;用户删了简历,模板和署名也不丢。

### `docs/sql/apply-b2-20261005.sql`(B2 上线前 Frank 跑生产)

```sql
-- 站内投递 B2:简历原件 user_resumes、投递偏好 apply_prefs、投递 applications  2026-10-05
-- additive、幂等(IF NOT EXISTS);不动既有数据。
-- 惯例(db-push-minefield):建表一律手写 SQL 先行;只写文件不执行,Frank 审后手动跑生产。
-- 设计稿:docs/design/投递页-B2-实施方案-20261005.md §2。
-- 三张都是原生表(先例 employer-explore-20260918.sql),不是 Payload collection,不进 seed:
--   payload_locked_documents_rels 不补列;🔴 DB_PUSH=1 会提议删这三张表,一律答 N。
--
-- 跑法(生产):① 跑本文件 → ② 部署 B2 代码 → ③ 抽查:
--   SELECT count(*), pg_size_pretty(sum(length(file_b64))) FROM user_resumes;
--   SELECT status, count(*) FROM applications GROUP BY status;

CREATE TABLE IF NOT EXISTS user_resumes (
  user_id      integer PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,  -- 一人一份现行简历;替换 = 覆盖这一行;注销连删
  file_b64     text NOT NULL,              -- 原件 base64(pte_audio.b64 先例;Resend 附件本就要 base64)
  file_name    varchar(200) NOT NULL,      -- 上传时的原文件名(只给本人预览;发给雇主的附件名另起,见方案 §5)
  mime         varchar NOT NULL CHECK (mime IN (
                 'application/pdf',
                 'application/vnd.openxmlformats-officedocument.wordprocessingml.document')),
  size_bytes   integer NOT NULL CHECK (size_bytes > 0 AND size_bytes <= 5242880),  -- ≤ 5 MB(RESUME_MAX_BYTES)
  resume_text  text NOT NULL,              -- extractText 抽出的纯文字(≤ 20,000;本人与配岗用,不发雇主)
  uploaded_at  timestamptz NOT NULL DEFAULT now(),
  updated_at   timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS apply_prefs (
  user_id        integer PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  sender_name    varchar(60),              -- 英文署名(方案 §7 Q2);NULL = 还没填,第 1 步必填
  cover_template text,                     -- 求职信模板,带 {{title}} {{company}} {{name}} 占位,≤ 4,000 字;NULL = 用站上默认
  updated_at     timestamptz NOT NULL DEFAULT now(),
  created_at     timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS applications (
  id              serial PRIMARY KEY,
  user_id         integer NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  job_id          integer REFERENCES jobs(id) ON DELETE SET NULL,  -- ?reset=1 是 DELETE FROM jobs:RESTRICT 会让重灌失败,CASCADE 会静默抹掉投递史
  job_title       varchar NOT NULL,        -- 快照(SavedJobs 先例:岗下架后列表照样有字)
  company         varchar NOT NULL,        -- 快照
  status          varchar NOT NULL DEFAULT 'draft'
                  CHECK (status IN ('draft', 'sending', 'sent', 'replied', 'bounced')),
  cover_text      text NOT NULL,           -- 换好占位的这一封;draft 时就是草稿;≤ 4,000 字
  employer_email  varchar,                 -- 只存不下发;认领发送那一刻从 jobs.apply_email 抄来;draft 为 NULL
  reply_to        varchar,                 -- 这一封实际的回复地址:B3 = 用户注册邮箱,B4 起 = 中转地址
  relay_token     varchar(32) UNIQUE,      -- B4 起:32 位小写 hex;B3 为 NULL
  subject         varchar,
  body_text       text,                    -- 发出那一封的固定正文原文
  resume_file     varchar,                 -- 附件名快照
  cover_file      varchar,
  resend_id       varchar,                 -- Resend 返回的 id;退信回调按它对账
  sent_at         timestamptz,
  first_reply_at  timestamptz,             -- B4:首次雇主回信(回复率只算得出下限)
  created_at      timestamptz NOT NULL DEFAULT now(),
  updated_at      timestamptz NOT NULL DEFAULT now()
);
-- 一人一岗一行:草稿原地升级成已投递;job_id 置空后不再撞(NULL 互不相等)
CREATE UNIQUE INDEX IF NOT EXISTS applications_user_job_uq ON applications (user_id, job_id);
-- 我的求职列表、每人 24 小时 20 封、批 C 一辈子 3 封
CREATE INDEX IF NOT EXISTS applications_user_sent_idx ON applications (user_id, sent_at DESC);
-- 全站当日发信预算(Resend 免费档每天 100 封,收信也算)
CREATE INDEX IF NOT EXISTS applications_sent_at_idx ON applications (sent_at) WHERE sent_at IS NOT NULL;
-- 退信回调对账
CREATE UNIQUE INDEX IF NOT EXISTS applications_resend_id_uq ON applications (resend_id) WHERE resend_id IS NOT NULL;
```

### `docs/sql/apply-relay-<B4 当天>.sql`(B4 跑)

```sql
CREATE TABLE IF NOT EXISTS application_messages (
  id               serial PRIMARY KEY,
  application_id   integer NOT NULL REFERENCES applications(id) ON DELETE CASCADE,
  direction        varchar NOT NULL CHECK (direction IN ('in', 'out')),  -- in = 雇主 → 用户;out = 用户回复 → 雇主
  resend_email_id  varchar NOT NULL UNIQUE,  -- email.received 的 data.email_id:回调重试 / 重放去重
  message_id       varchar,                  -- 原信 Message-ID,串 In-Reply-To / References
  from_addr        varchar NOT NULL,
  subject          varchar,
  body_text        text,                     -- 站内看原文(Resend 只留 30 天,当场入库)
  attachment_names jsonb,                    -- 附件名清单(本体不存)
  forwarded_at     timestamptz,              -- NULL = 还没转成功,回调重试时补转
  received_at      timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS application_messages_app_idx ON application_messages (application_id, received_at);
CREATE TABLE IF NOT EXISTS bounced_emails (
  email        varchar PRIMARY KEY,          -- 小写
  bounce_type  varchar NOT NULL,             -- Permanent / suppressed
  first_at     timestamptz NOT NULL DEFAULT now()
);
```

- 列表、元信息查询一律不取 file_b64,只在预览和发送时按单行取。cms 堆约 256MB:发一封时内存里同时有约 6.7MB 的 base64 串加一份 JSON 请求体。
- 投递条数(每人 24 小时 20 封、批 C 的 3 封)一律数 applications 行。进程内的 checkLimit 每次部署或 OOM 重启都会清零(`cms/src/lib/quota/variables.ts:14`),只用来防刷。

## 3. 接口

**写在前面**:

- 线格式就是包与包之间的契约。客户端照「形状本域自声明」各写各的 type,不跨域 import。
- 所有芯都用 `getUserOrNull`,鉴权出故障时回 401,不回 500(`cms/src/lib/quota/functions.ts:48`)。
- 连接池只在 routes.ts 里 `getDb()`。

### 投递页本身(不是 HTTP 接口)

- 路由:`GET /apply/<id>?step=resume|letter|preview|done`。
- 页面门调两样:`lib/resume/server` 的 `loadResumeMeta({db,userId})`,和 `lib/apply/server` 的 `loadApplyStart({db,userId,job})`(返回署名、按本岗填好的信、草稿状态、发出时刻)。
- 起始步:
  - 没简历、没署名或三题没答,落第 1 步;
  - 有模板(以后再投),落预览;
  - 已发出,落已投递;
  - 地址里的 `step` 只能往回跳,不能跳过没做完的步。
- 未登录:`redirect` 回 `/jobs/<id>`。岗已下架且没投过:同样回职位页。
- 不进索引:robots 加 `/apply`,meta 设 `index:false`。

### applySendRoute 的顺序

1. 认人;
2. 取草稿、简历、雇主邮箱;
3. 查额度;
4. 【批 C 挂点:`isPro(user) === false` 且已发数 ≥ `FREE_APPLY_LIFETIME`,回 402 `PAYMENT_REQUIRED`(`cms/src/lib/http.ts:39`);投递页收到 402 弹 pricing 桶的定价框】;
5. 服务端再判一次字符(和客户端调同一个函数);
6. 认领:`UPDATE … SET status='sending' … WHERE id=$1 AND status='draft' RETURNING id`。拿不到行回 409。停在 sending 超过 10 分钟的行算作可重新认领;
7. 渲染 PDF;
8. `postMail`;
9. 成功写 sent 和 resend_id;失败或 dry-run 退回 draft,并留痕。

### 代发(B3)

请求:`POST https://api.resend.com/emails`,头 `Authorization: Bearer <RESEND_API_KEY>`、`Idempotency-Key: apply-<投递号>`。

```json
{
  "from": "\"Wang Peng via Offer2PR\" <apply@offer2pr.com>",
  "to": ["<employer_email>"],
  "reply_to": "<用户注册邮箱>",
  "subject": "Application for <title> - <company>",
  "text": "<固定正文>",
  "html": "<同一段正文转义后一行一个 <p>>",
  "attachments": [
    { "filename": "Wang_Peng_Resume.pdf", "content": "<file_b64>", "content_type": "application/pdf" },
    { "filename": "Cover_Letter_Acme_Foods.pdf", "content": "<PDF base64>", "content_type": "application/pdf" }
  ],
  "tags": [{ "name": "app", "value": "<投递号>" }]
}
```

- 返回的 `{id}` 写进 applications.resend_id。
- 字段依据:https://resend.com/docs/api-reference/emails/send-email 、 https://resend.com/docs/dashboard/emails/attachments 。整封信 base64 后上限 40MB。
- 幂等:同一个键 24 小时内重放,返回原结果;**载荷不同会回 409 `invalid_idempotent_request`**(https://resend.com/docs/dashboard/emails/idempotency-keys )。所以 PDF 用 `PDFDocument.create({ updateMetadata: false })`,不写生成时间,保证同一封重渲逐字节相同;测试里锁住这一点。
- 发件人:
  - 发件域 offer2pr.com 已经验证过(提醒信就是从 alerts@ 发的),apply@ 不用另建;
  - 显示名用署名转成 ASCII 的写法(去掉重音),并去掉 `"` `\` `<` `>` 和换行,防止头注入;
  - PDF 里用署名原文(西文重音可以)。
- 附件名:
  - 简历 `<署名 ASCII>_Resume.<pdf|docx>`;
  - 求职信 `Cover_Letter_<公司 ASCII>.pdf`。
  - 转换规则:NFKD 去重音,非字母数字一律换成 `_`,最长 60 字;转完是空的就用 `Resume.pdf` 或 `Cover_Letter.pdf`。原文件名只用在本人预览。
- 正文:从 `cms/src/components/jobs/constants.ts:2463-2520` 搬来,改成「附上简历和求职信」,署名换成英文名。

### 中转回信(B4)

- **令牌**:`crypto.randomBytes(16).toString('hex')`,32 位小写(邮件系统可能把本地部分转成小写),UNIQUE。地址 `reply-<令牌>@reply.offer2pr.com`。解析时匹配 `^reply-([0-9a-f]{32})@`,对 `to` 和 `received_for` 都转小写再找。找不到对应投递:留痕,回 200(不让 Resend 重试刷屏)。
- **验签**(https://resend.com/docs/webhooks/verify-webhooks-requests 、 https://docs.svix.com/receiving/verifying-payloads/how-manual ):
  - 用 `await req.text()` 拿原始请求体;
  - 签名内容是 `${svix-id}.${svix-timestamp}.${body}`;密钥取 `whsec_` 后面那段,base64 解码;HMAC-SHA256 后 base64;
  - `svix-signature` 头里有多个空格分隔的 `v1,<签名>`,逐个用 `timingSafeEqual` 比;
  - 时间戳偏差超过 300 秒就拒。
  - 用 node crypto 自己写,不加 svix 依赖。
- **email.received**(回调里只有元数据,https://resend.com/docs/webhooks/emails/received ):
  1. 按 `data.email_id` 去重(application_messages.resend_email_id 是 UNIQUE)。
  2. `GET /emails/receiving/{id}` 拿 html、text、message_id、`authentication`(https://resend.com/docs/api-reference/emails/retrieve-received-email )。html 默认把内嵌图片转成 data URI,所以**不用装 mailparser**。
  3. `GET /emails/receiving/{id}/attachments` 拿附件(下载链接 1 小时过期),内嵌的跳过(https://resend.com/docs/api-reference/emails/list-received-email-attachments )。附件合计超过 10MB 就不带附件,在转发信里写明附件名。cms 堆约 256MB,扛不住大附件。
  4. 先入库(forwarded_at 为 NULL),再转发。转发失败回 500,Resend 会按 5 秒 / 5 分 / 30 分 / 2 时 / 5 时 / 10 时的节奏重试(https://resend.com/docs/webhooks/retries-and-replays );重试进来时只补转 forwarded_at 还是 NULL 的那条。
- **判方向**:
  - 发件人等于该用户的注册邮箱,而且 `authentication` 里的 dkim 或 spf 是 pass:当作「用户回复雇主」。发给 employer_email,from 是「<署名> via Offer2PR <apply@>」,reply_to 是中转地址,带 `headers: {"In-Reply-To": <雇主上一封的 message_id>, "References": <历史 message_id 用空格串起来>}`。
  - 其他情况:当作「雇主来信」。转给用户的注册邮箱,标题写成 `[Offer2PR] <岗位名> - <公司>: <原标题>`,reply_to 也是中转地址。applications 的状态改成 replied,首次回信时刻为空时补上。
- **email.bounced / email.suppressed**(https://resend.com/docs/webhooks/emails/bounced ):
  - 按 `data.email_id` 等于 resend_id 找到那条投递;
  - Permanent 退信和 suppressed:状态改 bounced,邮箱写进 bounced_emails;
  - Temporary 退信只留痕;
  - 雇主邮箱进了 bounced_emails,发送接口就回 410,板上也不再出这个岗。
