# 缺数据不上线,Opus 本地修复(2026-09-28 立项)

> 起因:2026-09-28 Frank「gc jobs 和 CareerBeacon 来源的 jobs 经常数据不全啊」。查下来三类原因:新帖先上板、分类和整理晚一轮;源页上写了我们没抽;qwen 猜的工时 / 雇佣期常错(国会图书馆研究技术员被标成兼职,原文没这说法)。
> 拍板(同日,原话):「jobs 和公司可以分开存储吗?就是上线只保留全的数据的信息。然后在单独列文件包含不全的。然后我本地用 opus 来修复,不用 qwen 来修复数据了」「qwen 不准」「只要缺数据的,都让 opus 修」「只要数据不全的都不上。等本地我用 opus 修完才上」「不全的公司也不上」「先出设计稿」。
> 一句话:**线上只放齐全的岗和公司;不全的进待修清单,Frank 本机用 Opus 修,每格附出处原句、程序核对通过才采用,下一轮汇装上线;qwen 退出补数据。**
> 同日补拍(试跑之后):「是不是用我自己的搜索和数据线?opus 优先做整理,如果实在没有信息,先抓数据」—— **抓取全走本站自己的数据线(crawl 层缓存原文 → 各源解析),Opus 不自己上网,只读我们缓存好的原文做整理;缺信息先抓,抓完还没有才算「原帖没写 / 查无」。**

## 一、用户故事

**求职者小王**在职位板往下翻。每一行六格都有着落:要么有值,要么是「—」(原帖本来就没写,比如雇主没写薪资)。他不会再看到一行「未分类」连带 EE 类别、省提名、大分类、职业、vs 中位一排空格,也不会看到被模型猜错的「兼职」。
**做成的标志**:板上任意一行,「—」只出现在原帖没写的格子上。

**小王点开一家公司**。要么看到核实过的信息卡(官网、总部、简介),要么只看到公司名 —— 没有半截卡,也没有模型猜的总部。

**Frank 修数据**。在本机开 Claude Code(Opus),打 `/repair`。它从待修清单取一批,岗位读原帖、公司上网查官网,逐格填值并给出处原句;核对脚本当场过一遍(值合不合法、原句是不是真在原帖或那张网页里),通过的写进修复库,不过的说明原因退回重看。下一轮汇装(一小时内)这批就上线。
**做成的标志**:待修清单的条数一天天往下走;线上每一格都能指回原帖结构化字段、原帖一句原文,或官网一句原文。

## 二、「全」怎么算

每一格三种状态:**有值** / **原帖没写**(或公司「查无」:Opus 查过、确实没有,记下来)/ **缺**(还没人看过)。前两种算全,第三种不算。「原帖没写」上线显示「—」。

### 岗位:职位板那一行的六格

| 格 | 算数的来路 | 不算数 |
|---|---|---|
| 职业分类(NOC) | 原帖官方码(Job Bank)、本站标题规则、Opus 修复 | qwen 分类器(classify 域) |
| 工时 | 原帖结构化字段、程序从原文抽(CareerBeacon 标签、GC Jobs 任期栏)、Opus 修复 | jdformat 整理版顺带抽的 |
| 雇佣期 | 同上 | 同上 |
| 薪资 | 原帖字段、汇装薪资段从正文抽、Opus 修复 | — |
| 省 | 原帖地点、汇装地点段、Opus 修复 | — |
| 城市 | 同上 | — |

- **职业分类没有「原帖没写」**:每条岗总有一个职业。Opus 判不出(「Join our team,多个职位」这类)就记「判不出」,这条岗不上线,留在清单里给 Frank 看。
- EE 类别、省提名、大分类、职业、vs 中位都从这六格派生,不单列。
- 岗位齐全就上线,不看公司全不全(公司不全只影响公司信息卡)。

### 公司:官网、总部、行业、简介四格

| 格 | 算数的来路 | 不算数 |
|---|---|---|
| 官网 | 搜索 / Google 地点 / 招聘帖里找到的官网(company 域 findsite、places)、Opus 修复 | — |
| 总部 | 维基数据(Wikidata「总部所在地」)、Opus 修复 | 官网七节里 qwen 抽的总部(sites 域)、搜总部台里模型抽的 |
| 行业 | 公立机构按名字规则判的「公司分类」(确定性)、Opus 修复(私营按本站 15 类) | explore 的 qwen 判的、按在招岗反推的「推断」 |
| 简介 | ATS 公司档自带的简介(雇主自己写的)、Opus 修复 | qwen 写的 aiBrief(company 域 brief 步,11,303 条全是 qwen) |

- 公司「查无」:Opus 查过确实没有官网(小店常见),记「查无」,卡上照现有「没有官网」那一行灰字显示,算全。总部查不到公开信息、只有一个经营地点的,以招聘帖里的地址为总部(原句出自帖子)。
- 行业一格在信息卡上本来就不显示,但它管雇主板筛选与「相似雇主」;要全才算全。

## 三、岗位怎么「不上」

助手实查灌库逻辑(`cms/src/lib/mart/functions.ts`、`cms/src/lib/db/sql.ts` 关岗五句)得出:**光从 jobs.json 里拿掉,线上并不会下线**——
- Job Bank 岗:库里原样挂到发布满 30 天(只有 CLOSE_STALE 管它)。
- 板帖:CLOSE_UNSEEN_BOARD 有保护,某来源这轮在列不到库里在架的一半,整个来源这轮都不关(防抓坏了误下架)。Jobillico 98% 不全,正好触发,一条都不下。
- ATS:3 天后才关。
- 更要命:Job Bank 补抓详情正文、查投递邮箱、判死岗三步,靠汇装的 seen_ids 找活;岗从 seen_ids 里拿掉,正文就补不上,Opus 没得读。

所以分两种:
- **从没上过线的不全岗**:不进 jobs.json(不灌库),进待修清单。修好后作为新岗第一次灌进去,新岗提醒照常发。
- **已上过线、这一轮不全了的**(比如 qwen 填的值不算了):汇装写一张「扣下名单」`mart/held_jobs.json`(只有 externalId,形同 closed_jobs 那张对账表),灌库时照 CLOSE_DEAD_EXT 的做法关掉(status closed)。修好后它回到 jobs.json,灌库的 upsert 自己把它转回在招、清掉 closed_at,first_seen 不变(不重复提醒)。
- 两种都**照样记进 seen_ids**:后台补正文、查邮箱、判死岗照常找得到它们;板帖那道「过半」保护也不会误触发。
- 不另立「待修」状态:那要改库的状态枚举,再改职位页、站点地图、提醒各处的判断;扣下名单只多一张对账表、一条关岗语句,页面一处不动。代价:被扣下的岗打开显示「该岗位已下架」。
- 上线顺序:**cms 先认 held_jobs.json**(上传一张灌库不认识的表会让整轮灌库报错),推送换版后,ETL 才产出它。

## 五、先抓后整理(Opus 只做整理)

2026-09-28 试跑实测(20 条岗 + 5 家公司,Opus 子代理,核对脚本逐格复核):
- **准**:岗位 39 格,填出 10 格、标「原帖没写」29 格(每格附理由,如「casual dress 是着装不是临时工」「$ 是签约奖金」),原句 10 / 10 在原帖里;公司 20 格全部找到,程序重新打开出处网页,原句 20 / 20 都在。
- **贵**:岗位每条约 8 千 token、21 秒;公司每家约 3.8 万 token、2.8 分钟 —— 大头花在代理自己上网搜、反复抓页(大站拦自动访问,Home Depot 一家抓了 16 次)和每一轮重读整份材料上,真正判断用得很少。

所以四步,前两步不花模型:
1. **源页上已有的先抽干净**(确定性解析,同批 1 CareerBeacon 标签那样):Jobillico / Jobboom / Job Bank / HireAC / ATS 逐源查缓存页上有没有还没抽的结构化字段;没有正文的 790 条先补抓详情页。
2. **程序判「原帖没写」**:抓全以后,原帖全文(含结构化字段)里连一个相关字样都没有的格(薪资:金额、salary、salaire、wage…;工时:full-time、temps partiel、FTE、hours…;雇佣期:permanent、contract、contrat、casual、seasonal…),直接记「原帖没写」。现有 14,275 格是这种(薪资 5,301、雇佣期 6,740、工时 2,234)。
3. **其余交 Opus 整理**:只给标题 + 含相关字样的那几句(中位 610 字、平均 654 字,不给全文),一次调用塞约 40 条,不走带工具的代理。现有 18,612 条岗、31,678 格要它看(分类 6,444、雇佣期 13,405、工时 6,238、薪资 4,259、城市 818、省 514)。
4. **公司先走自己的数据线**:官网走 company 域 findsite(搜索)、官网三页走 sites 域抓进 crawl 缓存、总部先查维基数据;Opus 只读缓存页的文字做整理(取代 sites 域里 qwen 整理七节那一步)。缓存里没有官网页的,先排进抓取,抓到了再整理。原句对着缓存页核对,离线就能核,不用重新上网。

## 六、修复库与核对

新立 `etl/repair/` 域。回答的问题:**缺格的岗和公司谁来补、补得对不对、补完了没有**。它不判分类、不打模型;值由 Frank 本机的 Opus 会话给出,本域只管「待修清单 → 批次 → 核对 → 修复库」。工具域,不挂役(不进容器)。

- **待修清单**:`processed/repair/pending_jobs.json`、`pending_companies.json`,汇装每轮重写(大,不进 git)。岗位一条带 externalId、来源、链接、标题、雇主、发布日、缺哪几格、已有的格(只含算数的)、原帖正文;公司一条带 slug、名字、省、在招岗数、有没有人点开过、缺哪几格、已有的格、缓存里有哪几张官网页。岗位按发布日新→旧排,公司按「有人点开过 → 在招岗多」排。
- **批次只给相关的字**:岗位给标题 + 含相关字样的句子(第五节第 3 步);公司给缓存官网页的正文(首页、关于、联系三页,各截前几千字)。「原帖没写」由程序先判掉的格(第五节第 2 步)记 `by: rule`,不进批次。
- **修复库**:`processed/repair/jobs.json`、`companies.json`(进 git 留痕,同 classify 那张)。一格 = `{value, quote, url, note, by, at}`;`value` 为 null = 原帖没写 / 查无;`url` 只有公司格有(出处网页)。
- **四个手动件**:`--only next` 取一批(未修的,切成每份约 20 条的批次文件)、`--only accept` 收批核对、`--only status` 报进度、`--only test` 自测。
- **岗位核对**:
  - 值在合法词表里:NOC 必须是 `data/raw/noc/descriptions.json` 里 516 个五位码之一;工时 full / part;雇佣期 permanent / term / casual / seasonal;薪资是 Job Bank 写法(`$20.00 to $25.00 hourly`),数字必须出现在原句里;省是省码。
  - 原句逐字出现在原帖标题或正文里(折空白、不分大小写、弯引号与长短横线归一)。
  - 记「原帖没写」时,原帖里要真的看不到那一格的硬字样(薪资:带金额的 `$`;工时:full-time / part-time / temps plein / temps partiel;雇佣期:permanent position / temporary / seasonal 这类)。看得到就退回重看;确实无关(`$` 是签约奖金、permanent 是「永久居民」)写一句说明再交。
- **公司核对**:每格带出处网址 + 原句;出处必须是 crawl 缓存里有的页,程序对着缓存原文核原句(离线,不重新上网)。官网格额外核对:缓存页的标题或正文里出现公司名。简介由 Opus 写中英韩三语(信息卡本来就按界面语言显示),每句都要有出处,至少一句原句核对。缓存里没有能用的页 → 这家退回抓取队列(findsite / sites / 维基),抓到了再整理。
- **写回**:build 链在地点清洗之后、薪资清洗之前加一步 `mart --only repairs`:把修复库的岗位值「只填空」写回各仓(Job Bank / 各板 / ATS),后面的薪资归一、试点打标、评分照常处理它们。公司修复值在汇装公司段并入。原帖或程序已有值的格,修复库不覆盖。

## 七、`/repair` 技能(Opus 本机)

`.claude/skills/repair/SKILL.md`,Frank 打 `/repair`(可带 `jobs` / `companies` 与条数)。节奏:
1. `status` 报待修规模(含「等抓取」的公司家数)。
2. `next` 取一批,切成每份约 40 条岗 / 10 家公司。
3. 每份派一个 Opus 子代理,只读批次文件、只写结果文件,**不上网、不开别的工具**。红线写死:只搬运不发挥,每格给出处原句;批次里的字没写就记没写,不猜。
4. 主循环逐份 `accept`,汇报通过 / 退回条数;退回的按原因再派一轮。
5. 修完提醒:下一轮 build(一小时内)上线。
6. **定时跑**:qwen 原先在盒子上全天自动跑;换成本机 Opus、又有「不全不上」,新帖(每天约 1,000 条不全)要等跑一次才上线。在 Frank 电脑上设定时任务,每隔几小时自动跑一次 `/repair`,出门几天板子照常更新;不靠手动想起来。

岗位判法照 classify 域提示词的口径(按实际干的活判、主管类标题归主管码、不按雇主行业判),写进技能。**动工前先拿 classify 域的 161 条人工金标试 Opus 的分类准确率**,对着 qwen 的成绩看。

## 八、qwen 的活换成本机 Opus(2026-09-28 Frank「就是把之前 qwen 的角色换成线下的 opus 来做」「因为 qwen 老出错」)

| 类 | qwen 现在干的 | 换不换 |
|---|---|---|
| 会影响判断的数据 | 未分类岗判职业码(classify 域;定 TEER / 省提名 / EE / vs 中位) | 换 |
| | 整理版顺带抽的工时 / 雇佣期(jdformat;定省提名通道) | 换 |
| | 公司总部 / 简介 / 行业(sites 官网七节、company 搜总部台与简介步、explore 行业) | 换,只读本站抓好的缓存页 |
| | Jobillico / Jobboom 法文标题译英文(标题规则按英文标题判职业) | 换(1.3 万条短标题,量小) |
| | 公司名中韩译名(explore)、NOC 职业中文名(noc)、抽选通道中文名(pnp) | 换(短字串,随公司那一轮与一次性重译做掉) |
| 给人看的文字 | 整理版正文(jdformat,6 万条) | 先抽样查错率再定 |
| | 职位正文中韩译文、职位标题译名 | 先抽样查错率再定 |
| | 新闻译文(news)、PTE 题目翻译(pte) | 不属于补数据,不在这次范围 |

- **为什么第一类换**:这些值定的是一条岗能不能走省提名、是什么职业(09-27 Frank「千万不能搞错」)。实测 qwen 在正文没写 part-time 时判兼职只对一半,分类器对 Patent Examiner 这种明确标题也弃权;Opus 试跑 49 格全部附原句、全部核对通过,拿不准的都写了理由。按「只给相关句」做法,量也小(岗位存量约 500 万 token)。
- **为什么第二类先抽样**:量大一个数量级(6 万条正文的整理版加中韩译文,存量上亿 token,每天再加一两百万),出错代价也小(原帖随时点得开,整理版有数字核对)。先让 Opus 抽几百条查 qwen 的真实错误率,错得多的再换。
- **兜底的是核对,不是模型**:每格附原句、程序核对、能程序判的程序判 —— 不管用哪个模型都保留,Opus 也会错。

## 九、规模、用量与副作用(2026-09-28 实测,本地 mart)
