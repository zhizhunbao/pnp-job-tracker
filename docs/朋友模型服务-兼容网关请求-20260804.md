# 给模型服务加一层 OpenAI 兼容网关(请求 + 实测报告)

> 2026-08-04。写给维护那台 qwen3.6 服务的朋友(以及帮他改的 AI)。
> 背景:我们的站(offer2pr.com,加拿大移民/职位数据)有三处功能在调你这台服务:
> **简历对照 JD、职位描述整理、移民问答对话**。用得很顺,先谢。
> 下面两个问题是我们实测出来的,都能稳定复现;第 3 节是想请你加的东西,**很小,不破坏你现在的用法**。

---

## 1. 实测问题一:长度参数被忽略

**现象**:请求里带长度上限,服务端不理会,照样吐满。

**怎么测的**:同一段 prompt(尾部加随机 nonce 绕开缓存,确认回包 `cached=false` 是真生成),
分别用四种常见字段名各发一次,值都设成 24:

| 字段名 | 结果 |
|---|---|
| `max_tokens` | 忽略 |
| `num_predict` | 忽略 |
| `options.num_predict` | 忽略 |
| `max_new_tokens` | 忽略 |

五次回包**全是 371 字符的完整输出,一字不差**。

**为什么我们在意**:我们要的是「六到八句话」的短答复。现在只能在 prompt 里求它短,
再在自己这边按句截断——截断点不可能永远优雅,而且白烧 token。

## 2. 实测问题二:按 prompt 前 ~2000 字符做缓存键 ⚠️

这条比上一条严重,**它会让不同的请求拿到同一个答案**。

**怎么测的**(二分):构造两个 prompt,**只有尾部不同**,前缀逐步加长:

| 前缀长度 | 第二次请求 |
|---|---|
| 1,902 字符 | `cached=false`,真生成(正确) |
| 2,199 字符 | **`cached=true`,直接返回第一次的答案** |

也就是说:**超过大约 2000 字符之后的内容不参与缓存键**。

**补测(同一天,更精确)**:

| 项 | 实测 |
|---|---|
| `prompt` 字段 | 按**前 2000 字符**做键(差异点 @1990 不命中 / @2010 命中) |
| `system` 字段 | **也进键,但只截前 512 字符**(@490 不命中 / @522 命中) |
| 两者预算 | **各自独立** |
| `/api/translate` | **同样的 2000 截断**(2465 字符文本只有尾段不同 → 第二次 `cached=true`,译文一字不差) |

`system` 只有 512 字符进键这条尤其反直觉——它会翻掉「把变量放 system 里就安全」的想法。

**这对我们意味着什么**(三条都是实测,不是假设):

1. **写在 prompt 尾部的指令等于没写。** 我们连着三次改「结尾不要给建议」,毫无效果——
   一直在拿缓存。同样的话挪到 prompt 开头,立刻生效。
2. **⚠️ 已经在串答了,不是风险是事故。** 我们的简历对照功能 prompt 是「说明 + 职位描述 + 简历」,
   职位描述一长(我们库里 28% 的职位描述超过 1900 字),**简历整段就落在缓存键之外**。
   实测:同一份职位描述 + 两份完全不同的简历 → 第二次直接返回第一份的分析结果,一字不差。
   **这是跨用户数据泄露**(付费用户那条还会把别人简历里的内容改写出来),我们已经紧急修了。
3. **测试会被钉死。** 我们有个用例长期是绿的,加了指纹前缀后才发现:它绿只是因为某次幸运的输出
   被缓存钉住了,真实通过率大约 2/3。**缓存把 bug 藏了不知道多久。**

**我们目前的绕法**:在 prompt 首行钉一个内容哈希(`[ref:xxxx]`),让任何输入变化都必然改键。
这治标——它对你的服务来说等于缓存永远不命中(除非完全相同的输入),浪费你的算力;
而且每加一个新功能都要记得这件事。所以才有下面第 3 节的请求。

我们目前的绕法:把「身份信息」(用户原话、数据指纹)全部钉进 prompt 开头。
这治标,但只要模板一长就会重犯,而且每个新功能都要重新踩一遍。

## 3. 想请你加的:一个 OpenAI 兼容端点

**不用动你现在的 `/api/chat`**,新增一条即可,老的照旧跑。

```
POST /v1/chat/completions
```

请求体(标准 OpenAI 格式,我们只用这几个字段,**其余一概不需要**):

```jsonc
{
  "model": "qwen3.6",
  "messages": [
    { "role": "system", "content": "..." },
    { "role": "user",   "content": "..." }
  ],
  "max_tokens": 900,        // ← 请真的生效
  "temperature": 0.2,
  "stop": ["\n\n\n"],       // 可选
  "stream": false           // 若能支持 SSE 流式更好,不支持也不影响我们
}
```

响应体:标准 `choices[0].message.content` 即可。

### 三条硬需求(按重要性排)

1. **`max_tokens` 真的生效。**
2. **缓存键要覆盖完整请求**(整个 messages 的哈希),而不是前 N 个字符。
   如果实现成本高,**退一步也行:给一个关掉缓存的开关** —— 请求头 `X-No-Cache: 1`
   或 body 里 `"cache": false`,我们在需要精确的调用上带着它。
3. **错误用标准结构 + 正确状态码**。现在 prompt 超长会返 400,但没有机器可读的错误码,
   我们只能靠猜。给个 `{"error": {"type": "context_length_exceeded", "message": "..."}}` 就够了。

### 两条「有更好,没有也行」

4. **prompt 长度上限**:我们实测到大约 **6000 字符**(超了 400)。
   如果能提高,我们就能把更多官方事实喂进去、答复质量更好;
   提不了也没关系,**但请告诉我们准确的上限值**,我们照着切。
5. **流式(SSE)**:我们的对话功能一次要等十几秒,流式能让用户少等。

## 4. 一个请求:内容不要落盘

我们有个功能是**简历对照职位描述**,用户的简历文本会经过你这台服务。
我们在自己的隐私政策里写明了:服务端日志只记录文本长度与耗时、不记内容。

想确认/请求你那边也是同样口径:**不要把请求正文写进日志或落盘**,
也不要用于任何训练。如果你现在有日志,麻烦关掉正文部分——
这不是信不过你,是我们对用户的承诺得对得上实际。

## 5. 验收清单(你那边跑得通就算完)

```bash
# ① max_tokens 生效:输出应该被截短
curl -s $BASE/v1/chat/completions -H 'Content-Type: application/json' -d '{
  "model":"qwen3.6","max_tokens":24,
  "messages":[{"role":"user","content":"用三百字介绍加拿大安大略省"}]}' | head -c 400

# ② 缓存键覆盖全文:两条只有尾部不同的长 prompt,应返回不同内容
#    (把 XXXX 换成 3000 字的相同前缀,尾部分别接 "答:苹果" / "答:香蕉")

# ③ 关缓存开关(若实现了)
curl -s $BASE/v1/chat/completions -H 'X-No-Cache: 1' ...   # 同一请求连发两次,内容应不同

# ④ 超长报错:发一个超过上限的 prompt,应返回带 error.type 的 JSON 而不是裸 400
```

## 6. 如果只想做最小的一件

**做第 2 条(缓存键或关缓存开关)。** 长度参数我们能在自己这边兜,
但「不同输入拿到同一个答案」我们兜不了——那是会给用户看到错误内容的问题。
